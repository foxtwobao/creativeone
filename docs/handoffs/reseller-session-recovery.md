# Reseller 登录会话恢复与应用授权修复建议

> **状态更新：原会话恢复建议已被 Reseller 持久 Key 方案取代。** 对方交接文档为 `/home/hulei/projects/tokenone_reseller/docs/CREATIVEONE_RESELLER_MIGRATION.md`。Reseller 已报告完成升级，日常 ensure 使用持久 Key，不再依赖原生登录会话；历史用户需完成一次现有授权流程。CreativeOne 已完成配套提示和请求关联日志调整，不新增登录恢复模式或错误码。下文保留为旧问题证据和当时的建议，不能继续作为当前实现清单；真实授权升级及会话失效后的后台查询仍待验收。

## 目标与范围

解决 CreativeOne 后台查询视频任务时，关联服务中断后被要求重复授权的问题。

本文是交给 `tokenone_reseller` 项目的修改需求和验收依据，尚未在该项目实施。正常服务重启应保留已有授权；登录凭据确实无法恢复时允许要求重新登录，但应与重新同意应用授权区分。

## 1. 已确认的现场证据

- CreativeOne 任务：`10d0f5f1-19cd-4975-989c-0c912e3a0eb5`。
- 模型：`wan3.0-video-720p`。
- 上游任务：`task_p5vKrerwN7ytVj5DzvqwJScu0cOT3wyD`，已创建，不应重新提交生成。
- 用户反馈 Reseller 和 IDONE 曾停止，之后重新启动。
- CreativeOne 后台先记录 `APP_KEY_RECOVERY_UNAVAILABLE`，后记录 `APP_USER_AUTHORIZATION_REQUIRED`；任务保留为暂停状态。
- 只读查询当前 Reseller 数据库：`creativeone` 的 `application_grants` 记录存在，关联的 `gateway_sessions` 尚未到期，但 `state='refreshing'`。

**可以确认**：后一次错误由不可用的登录会话触发，不能解释为应用授权自然到期。`application_grants` 当前没有独立的到期字段。

**尚未确认**：哪一次刷新请求导致会话留在 `refreshing`，当时上游是否已经轮换凭据，以及之前读取 Key 失败的具体 HTTP 状态。需要在 Reseller / New API 的对应日志中补齐证据，不能仅凭服务曾停止推断全部因果。

### 更正此前诊断

当前实际调用的是 `tokenone_reseller`，不是旧 `tokenone_enhance`。

当前 Reseller 的 `APP_KEY_RECOVERY_UNAVAILABLE` 来自 `RevealModelKey` 调用失败或返回空 Key，不能据此认定加密密钥不一致或密文解密失败。此前依据旧 Enhance 同名错误作出的解密失败判断撤回。

## 2. 当前实现的问题

以下路径均相对于 `tokenone_reseller` 仓库。

| 位置 | 当前行为 | 问题 |
| --- | --- | --- |
| `internal/auth/application_session.go` · `ApplicationSessionToken` | 只读取未过期且为 `ready` 的会话 | 无记录、过期、已撤销、刷新结果不明等情况被合并为登录失效 |
| 同上 | 刷新前持久化 `refreshing`；刷新结果不明时保留该状态 | 防止重复使用轮换凭据是必要的，但后台应用缺少明确恢复出口 |
| `internal/server/application_keys.go` · `ensureApplicationKey` | `ErrNativeLoginRequired` 映射为 `APP_USER_AUTHORIZATION_REQUIRED` | 已授权但登录不可用，被显示为“请授权” |
| `internal/server/application_authorization.go` | grant 直接关联 gateway session；撤销时清空关联 | 授权状态与会话关联耦合，不能仅凭 grant 记录存在就认定仍有有效同意 |
| `internal/gateway/managed.go` | 已支持丢弃不可用浏览器会话后重新登录 | 应用侧恢复流程需要复用并接通，避免另造登录流程 |

当前 `refreshing` 是防止凭据重放的持久化标记，不是可以在重启时直接清除的临时标记。

## 3. 必须调整的行为

### 3.1 区分应用授权、登录会话和服务故障

至少区分以下结果，不要都返回“需要授权”：

| 情况 | 建议接口语义 | 用户操作 |
| --- | --- | --- |
| 从未授权或用户主动撤销 | 保留 `APP_USER_AUTHORIZATION_REQUIRED` | 用户明确同意授权 |
| 已授权，但会话过期或凭据明确失效 | 独立的“需要重新登录”错误 | 重新登录并恢复关联 |
| 刷新结果不明，无法安全恢复 | 独立的“登录会话需要恢复”错误，可与重新登录共用一个外部错误码 | 通过登录流程取得新会话 |
| 上游暂时不可用、网络故障、数据库故障 | 服务不可用错误 | 修复服务后继续原任务，不诱导重新授权 |
| 用户停用、身份不匹配、应用撤销、分组权限拒绝 | 保留对应明确拒绝 | 不自动恢复权限 |

新错误码名称由 Reseller 的契约统一确定，并同步文档和调用方。可考虑 `APP_USER_LOGIN_REQUIRED`，但不能仅恢复旧错误码而遗漏接口及 CreativeOne 适配。

无需为每种内部失败新增一个公开错误码；内部日志保留可区分原因即可。

### 3.2 保留刷新互斥和防重放，补齐中断恢复

- 继续复用应用和浏览器共用的刷新锁，确保同一会话只有一个凭据轮换者。
- 在持锁后读取最新会话状态，避免另一请求已经刷新成功，却继续使用旧凭据。
- 刷新成功后，验证用户身份，并将新凭据、有效期和 `ready` 状态原子保存。
- 刷新结果不明时禁止重放旧 refresh cookie；不能在启动时把所有 `refreshing` 改成 `ready`。
- 只有上游契约或可靠证据能够证明凭据未被消费时，才可恢复原凭据；单独一个网络错误、超时或 5xx 不足以证明。
- 如果没有可安全查询或恢复轮换结果的上游能力，明确转入重新登录恢复流程，不承诺纯后台一定能修复。
- 正常 `ready` 会话重启后应直接可用，不能因重启要求重新授权。
- 不新增定时重试、超时或重试次数等默认值；如确需新增，先说明适用环节及失败行为并确认。

### 3.3 已授权用户恢复登录后重新关联会话

- 优先复用现有原生 OAuth / IDONE 登录入口及 PKCE 返回流程。
- 如果 IDONE 登录仍有效且现有协议支持，可减少用户重复输入；不可承诺所有情况下都能无感恢复。
- 新会话必须重新验证 issuer、subject 和上游 user ID，与原应用授权身份一致后才能关联。
- 原授权仍有效、应用与权限范围未改变时，不应因为换了登录会话再次要求同意同一授权。
- 主动撤销必须继续生效，不能通过“恢复登录”绕过撤销。当前撤销以清空 `gateway_session_id` 表达，调整设计时必须保留可区分的撤销语义；按最小改动选择记录授权状态或等价机制。
- 其他账号登录、身份不匹配时拒绝关联，不能按邮箱猜测身份。
- 恢复后只继续获取 Key / 查询原任务，不重放视频创建请求。

### 3.4 明确后台任务与浏览器会话的关系

CreativeOne 当前在服务器每 5 秒查询视频状态，浏览器关闭后仍需继续工作。每轮获取 Key 都经过 Reseller 的身份和授权校验。

本次最低要求是：明确区分同意授权和登录恢复，修复中断后的恢复出口。**它不等于已经实现永久脱离登录会话的后台授权。**

如果产品要求用户长期离线、登录会话过期后也能继续后台处理，需要另行确定服务端应用凭据的生命周期、权限范围与撤销机制。不能通过缓存过期 Key、跳过身份校验或静默延长会话来实现，也不应把这项扩展混入当前故障修复。

### 3.5 增加能定位问题的日志

记录请求关联 ID、应用 ID、内部会话关联标识、处理阶段、状态变更和上游 HTTP 状态。重点区分：

- 会话缺失 / 到期 / 已撤销 / 刷新结果不明。
- 身份校验失败、刷新请求失败、新凭据保存失败。
- `RevealModelKey` HTTP 失败、空结果、响应解析失败。

不得记录 Key、访问令牌、refresh cookie、授权 code、应用凭证或完整上游敏感响应。日志应足以关联 CreativeOne 的请求，不依赖人工反复触发生成。

| 文件 | 修改重点 |
| --- | --- |
| `internal/auth/application_session.go` | 明确错误分类，保留刷新锁与轮换保护，提供恢复所需的状态信息 |
| `internal/newapi/session.go` | 在不泄露凭据的前提下保留失败阶段和状态；不自动重试轮换请求 |

## 6. 验收清单

1. **正常重启**：已有授权、未过期的 `ready` 会话在 Reseller / IDONE 重启后仍能查询原任务，无重复授权。
2. **访问凭据正常过期**：安全刷新一次，新凭据落库，后续查询成功。
3. **刷新结果丢失**：模拟上游已轮换但响应丢失，不重放旧 refresh cookie；给出可执行的登录恢复入口。
4. **刷新进程中断**：分别在标记刷新后、发送请求后、收到响应后、保存新凭据前中断；恢复后不永远显示普通“未授权”，也不绕过轮换保护。
5. **并发访问**：浏览器和多个应用请求同时使用同一会话，只发生一次有效轮换，无旧凭据重放。
6. **临时故障**：上游断连、5xx、数据库异常与未授权错误区分，不清空原应用同意记录。
7. **登录恢复**：同一身份登录后重新关联会话，原视频任务可继续查询；不同身份被拒绝。
8. **授权撤销**：主动撤销后重新登录不能静默恢复应用授权；需要用户重新同意。
9. **会话真实到期**：显示登录恢复提示，不将其解释为同意记录自然到期。
10. **Key 读取失败**：能从脱敏日志分辨失败阶段；不得再直接归因为密文解密错误。
11. **浏览器关闭**：只要服务端凭据仍有效，视频后台查询和落盘继续进行；重新打开后能看到结果。
12. **原任务保护**：整个恢复过程不新增视频生成 POST，不产生重复任务或重复生成费用。

当前案例处理时保留原记录和诊断证据，不直接修改 `refreshing` 状态或删除授权记录作为修复。
